# BearingGuard AI — ML Training Report

Generated by `backend/train_model.py`. Re-run it any time to regenerate
`fault_classifier.joblib`, `rul_regressor.joblib`, and `metrics_report.json` —
this file is the human-readable narrative version of that same run.

## 1. What data was actually used, and why

The project's only real sensor data is `backend/bearing2_features.csv` /
`bearing2_anomalies.csv`: **Test 2** of the NASA/IMS (University of Cincinnati
Center for Intelligent Maintenance Systems) bearing prognostics dataset — four
bearings on one shaft, vibration features sampled every 10 minutes from
2004-02-12 to 2004-02-19. The test was stopped because **bearing 1 developed a
genuine, documented outer-race defect**. This is stated in the dataset's own
README and confirmed by essentially every paper that cites this dataset — it
is not something this project inferred. **Bearings 2, 3 and 4 ran the entire
test without failure.**

That is one real, ground-truth fault outcome (bearing 1: outer-race failure),
not several. There is no genuine inner-race or ball/roller-defect example
anywhere in this project's data — that would require the *raw* vibration
files from IMS Test 1 (bearing 3 = inner race, bearing 4 = roller defect)
and/or Test 3 (bearing 3 = outer race), which are not present here; only
Test 2's already-extracted features are.

### The real attempt made to get the multi-fault raw data

- The full IMS dataset ("4. Bearings.zip") is publicly reachable, no auth
  needed, at `https://phm-datasets.s3.amazonaws.com/NASA/4.+Bearings.zip`
  (confirmed reachable, `Content-Length: 1,075,597,174` bytes).
- No Kaggle credentials exist in this environment (`pip show kaggle` → not
  installed, no `kaggle.json`), so Kaggle mirrors of this dataset were not an
  option without the user supplying an API token.
- Searched for a GitHub mirror that already publishes pre-extracted,
  multi-fault feature CSVs (would have been small enough to download
  quickly) — none of the repos found (`Miltos-90/Failure_Classification_of_Bearings`,
  `biswajitsahoo1111/data_driven_features_ims`, `Sruthi96200/NASA-Bearing-Dataset`)
  host a ready-made features file; they all re-download and process the raw
  archive themselves.
- Inspected the S3 zip's structure remotely (via the `remotezip` package, no
  full download needed for this step): it contains a single nested
  `IMS.7z` — meaning there is no way to selectively fetch just, say, Test 1's
  files without downloading the (compressed) archive; 7-Zip's format doesn't
  support the kind of cheap partial/ranged extraction a plain zip would.
- Measured real download throughput from this environment against that S3
  URL: **~150–450 KB/s** (sampled repeatedly; connection also timed out
  mid-transfer more than once). At that rate the 1.07 GB archive alone needs
  roughly **60–100 minutes**, before any time to extract the 7z (several GB
  uncompressed) or write and validate a raw-signal feature-extraction
  pipeline (RMS, kurtosis, and an envelope/BPFO-energy calculation requiring
  correct bearing geometry + shaft-speed constants — the original script that
  produced `bearing2_features.csv` isn't in this repo to crib from).
- A background download was actually started and observed progressing
  (reached ~140 MB of 1.07 GB) to confirm the above wasn't a one-off fluke,
  then stopped once it was clear it would not complete, be extracted, and be
  turned into a validated feature-extraction pipeline within the scope of
  this task without a rushed, higher-risk implementation.

**Conclusion:** obtaining genuine multi-fault-type raw data was judged
infeasible within this task's time budget, given the measured connection
speed and the amount of untested downstream engineering (7z extraction +
from-scratch signal processing) it would require. Rather than rush that or
fabricate labels, the models below are built from the Test 2 data that is
actually, verifiably present in this project — honestly scoped as described
next.

## 2. What was actually built

### 2a. Fault / health-state classifier — `fault_classifier.joblib`

**This is a binary Normal-vs-Anomalous classifier, not a multi-fault-type
classifier.** It cannot tell inner-race from outer-race from ball defects —
doing that honestly would require genuine labeled examples of each, which
this project's data doesn't have (see §1).

- **Model:** `RandomForestClassifier` (`n_estimators=200, max_depth=8,
  class_weight="balanced"`).
- **Features:** `rms`, `kurtosis`, `bpfo_energy` — the same three features
  the existing rule-based system already computes.
- **Rows:** all four bearings' Test 2 readings reshaped to one row per
  (timestamp, bearing) — 984 timestamps × 4 bearings = 3,936 rows.
- **Labels:**
  - Bearings 2, 3, 4 → `"Normal"` for every row. This is **genuine ground
    truth** (documented: these bearings did not fail in this test).
  - Bearing 1 → the already-computed z-score-onset label from
    `detect_anomalies.py`, collapsed to `"Normal"` / `"Anomalous"` (Mild +
    Severe merged). The *exact moment* this switches to Anomalous is
    **heuristic** (a z-score threshold against bearing 1's own healthy
    baseline), not a post-mortem inspection timestamp — but the fact that
    bearing 1 eventually failed and 2/3/4 did not is genuine.
- **Split:** chronological, not random — 75% of the shared timeline for
  training, the final 25% (which includes bearing 1's actual failure
  endgame) held out for testing. A random shuffle would have let the model
  train on points a few minutes away from ones it's tested on.
- **Deployed artifact:** refit on 100% of the labeled data after validation
  (standard practice), so live inference benefits from the full trajectory.

**Measured results (held-out chronological test set, 984 rows):**

| Metric | Value |
|---|---|
| Accuracy | 0.936 |
| F1 (macro) | 0.915 |
| Precision / Recall — Anomalous | 0.86 / 0.89 |
| Precision / Recall — Normal | 0.96 / 0.95 |

Confusion matrix (rows = actual, cols = predicted; labels = [Anomalous, Normal]):

```

 [ 36 704]]
```

Feature importances: see `metrics_report.json` (`bpfo_energy` and `rms`
dominate, as expected — `kurtosis` contributes less).

### 2b. Remaining Useful Life (RUL) regressor — `rul_regressor.joblib`

- **Model:** `RandomForestRegressor` (`n_estimators=300, max_depth=10`).
- **Trained on:** bearing 1 only — **the one genuine run-to-failure
  trajectory** available. Target = hours remaining until the run's last
  reading (genuine ground truth, since the recording stops at bearing 1's
  actual documented failure).
- **Split:** chronological — first 70% of bearing 1's trajectory (163.8 hours
  total) for training, final 30% (the approach to failure) held out for
  testing. Also cross-validated within the training portion via
  `TimeSeriesSplit` (5 folds) as an extra sanity check.

**Measured results (held-out chronological test set, final 49.2 hours of the run):**

| Metric | Value |
|---|---|
| MAE | 28.53 hours (17.4% of the full 163.8h trajectory) |
| RMSE | 32.75 hours |
| R² | −4.29 |
| TimeSeriesSplit CV MAE (within training data) | 28.85h ± 13.43h |

**Why R² is negative, and why that's not a red flag being hidden:** the held-out
window covers only the last ~49 hours of a 164-hour run, so its own variance
is small — R² punishes real error heavily against that small denominator.
More fundamentally, `RandomForestRegressor` (like any tree ensemble) cannot
extrapolate past the feature magnitudes it saw in training, and the last
stretch before failure is exactly where RMS/kurtosis/BPFO-energy reach their
highest, never-before-seen values, so predictions there under-react. **This
is a documented, real limitation of applying tree-based regression directly
to RUL from a single degradation trajectory — read MAE/RMSE, not R², as the
metrics that matter here.**

A second, honest caveat: with only one physical unit's failure trajectory
available, this has been validated by holding out the *later part of that
same trajectory* — it has **not** been validated against a different
bearing's failure run. Whether it generalizes to a different bearing is
genuinely untested.

A concrete example of a related edge case, found while testing the deployed
model manually (see below): the *literal last reading* in this dataset has
RMS collapsed to near-zero — not because the bearing recovered, but because
the equipment had already failed/stopped by then (the existing rule-based
`db_tools.get_threshold_status` has explicit logic to catch this "dropout"
pattern). The ML models have **no awareness of that pattern** — fed that
exact final reading, `predict_fault_type` calls it "Normal" (confidence
1.0) and `estimate_rul` estimates 36.7 hours remaining. This is a genuine
limitation worth knowing about, not something papered over: the ML tools
answer "does this instantaneous reading look like the bearing is healthy or
degrading," not "is the equipment even still running."

## 3. How this was tested

The Supabase project configured in `backend/.env`
(`nnbciwjdvlnitlukkcak.supabase.co`) was **unreachable during this work** —
DNS lookups for it fail with NXDOMAIN on two independent resolvers (the
local network's DNS and Google's public 8.8.8.8), and the same failure
reproduces on the pre-existing, unmodified `db_tools.py` and the pre-existing
`/status` endpoint. This is a genuine infrastructure issue independent of
this change (most likely: the Supabase free-tier project was paused for
inactivity and has since been deleted, freeing the subdomain) — **not
something fixable by editing code**, and not something this work introduced.

Because of that, full live end-to-end testing against the real database
could not be completed. What was verified instead:

1. `train_model.py` runs clean and prints the metrics above.
2. `ml_tools.predict_fault_type` / `estimate_rul` were exercised directly
   against **two real historical rows** from `bearing2_anomalies.csv` (the
   peak pre-failure reading and the literal final reading), with Supabase's
   query chain mocked to return that row instead of a live network call —
   confirms the model-loading and inference code path is correct.
3. `main.py`'s FastAPI app was started locally: `/health` works; the new
   `/predict/fault-type` and `/predict/rul` return a proper 500 (not a
   crash) while Supabase is down — and the **pre-existing** `/status`
   endpoint returns the identical failure, confirming this is the DB outage,
   not the new code.
4. `agent.ask_agent()` was run for real against Groq (Groq itself is
   reachable) with the question *"What fault type is predicted for bearing 1
   right now, and what is its estimated remaining useful life?"*, Supabase
   mocked as in (2). The agent correctly called **both** new tools
   (`predict_fault_type` then `estimate_rul`) and produced an accurate,
   appropriately-hedged answer that respected the binary-classifier and
   RUL-uncertainty caveats from the system prompt.
5. Fixing (4) surfaced a real, pre-existing bug: `agent.ask_agent()` only
   passed `tools=` on the first LLM call, so a question needing a *second*
   tool call (natural now that there are two ML tools to combine) made Groq
   reject the follow-up with `400 Tool choice is none, but model called a
   tool`. Fixed by keeping `tools`/`tool_choice` available across a bounded
   multi-round loop (`MAX_TOOL_ROUNDS = 4`) instead of exactly one round.

**Before re-deploying**, the user should restore/re-point the Supabase
project (recreate it and re-run `push_to_supabase.py`, or update
`SUPABASE_URL`/`SUPABASE_SERVICE_KEY` in `.env` to a working project) and
re-verify `/status`, `/trend`, `/predict/fault-type`, `/predict/rul`, and
`/chat` all return real data — this affects the whole app, not just what was
added here.

  failures — it was validated on one trajectory's own held-out ending.
